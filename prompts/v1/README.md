## 1. Thresholds are test-only, not production policy

TASK-24 §5 defines five threshold parameters and **deliberately leaves their
values unset**. It remains the source of truth, and **final values are still
pending** TASK-18 and TASK-23.

Prompt V1 nonetheless cannot be executed without concrete numbers. They are
therefore isolated in a single file, [`test_thresholds.json`](test_thresholds.json),
which is the **only** place a numeric threshold appears anywhere in TASK-25:

- `prompt_v1.md` contains placeholder tokens (`{{T_DAMAGE_REPORT}}` and so on)
  and no values of its own.
- `render_prompt.py` substitutes them at render time and fails loudly on any
  unresolved placeholder.
- Replacing the values when calibration arrives requires editing that one file.
  The prompt and the runner need no changes.

The values used for this test run were chosen for exactly one reason: to place
the fixtures on both sides of every decision boundary so each branch of the
prompt is exercised. **They carry no empirical justification and must not be
cited as recommended or calibrated values.**

| Parameter | Test value | Purpose in this test |
|---|--:|---|
| `T_DAMAGE_REPORT` | 0.30 | `f03`, `f07` place detections below it |
| `T_DAMAGE_HEDGE` | 0.60 | `f07` places one detection in the hedge band |
| `T_PART_REPORT` | 0.50 | `f04` places a part below it |
| `T_ASSOC_STATE` | 0.60 | `f08` places an association below it |
| `T_ASSOC_AMBIG` | 0.10 | `f05` sets a candidate gap of 0.05 |

## 2. How the reports were generated

> [!IMPORTANT]
> **There is no LLM API integration in this repository.** No `ANTHROPIC_API_KEY`,
> no SDK, and no CLI are available in the project environment, so there is no
> scripted, re-runnable generation path yet. Building one is not in TASK-25's
> scope.

The outputs in `outputs/` were generated by an LLM executing the rendered
prompt — not authored by hand.

| Aspect | Detail |
|---|---|
| Model | Claude Sonnet 5 (`claude-sonnet-5`) |
| Invocation | Subagent dispatch, one independent agent per fixture |
| Run date | 2026-09-14 |
| Context isolation | Each agent started cold and received **only** its rendered prompt file. None saw TASK-24, the other fixtures, the other outputs, or the checker. |
| Input | `render_prompt.py <fixture>` output, written to a file the agent read |
| Instruction to agent | Treat the file as system prompt + user turn; write the resulting report text and nothing else to the output path; read no other repository file |
| Samples per fixture | 1 |

One agent per fixture was used deliberately: TASK-24 §6 forbids carry-over
between requests, and a single agent processing all nine in sequence could not
demonstrate independence.

**To regenerate**, render each fixture and give the rendered prompt to a model in
a fresh context:

```bash
python3 render_prompt.py fixtures/f01_high_confidence_single.json
```

### Limitations of this method

- **Single sample per fixture.** Nothing here measures run-to-run variance. A
  prompt that passes once may fail on resample.
- **No decoding control.** Temperature, top-p and seed were not set and are not
  recorded, so the runs are not reproducible in the strict sense.
- **One model only.** Results are specific to Claude Sonnet 5. Another model, or
  another version of this one, may behave differently.
- **Not an integration test.** The path from CV pipeline to prompt to report does
  not exist yet (TASK-29).

## 3. Fixtures and the branches they exercise

| Fixture | Case | Branch exercised | Expected behaviour |
|---|---|---|---|
| `f01` | High-confidence single finding | Step 4 → LOCATED | Plain statement, part named |
| `f02` | No detections | Step 3 → NO FINDINGS | Absence disclaimer; part detections **not** mentioned |
| `f03` | All damage below report threshold | Step 2 → SUPPRESSED ×2, Step 3 | No findings + appendix listing both |
| `f04` | Low-confidence **part** | Step 4 → UNLOCATED (part conf) | Damage stated, part **not** named |
| `f05` | Ambiguous association | Step 4 → AMBIGUOUS (gap 0.05) | Both candidates listed, unranked |
| `f06` | Unmatched damage | Step 4 → UNLOCATED (null part) | Damage stated, no location |
| `f07` | Multiple findings, mixed confidence | Steps 2–5, all branches at once | 2 plain + 1 hedged + 1 suppressed |
| `f08` | Low-confidence **association** | Step 4 → UNLOCATED (assoc conf) | Link not asserted despite confident endpoints |
| `f09` | Unusable image | Step 1 → halt | "Could not be assessed", **never** "no damage detected" |

`f04`, `f06` and `f08` deliberately separate the three independent confidence
values (TASK-24 §4.4). In each, the values that are high would license naming a
part if the model conflated them:

| Fixture | Damage conf | Part conf | Assoc conf | Why the part must not be named |
|---|--:|--:|--:|---|
| `f04` | 0.82 | **0.41** | 0.77 | The part itself is uncertain |
| `f08` | 0.81 | 0.87 | **0.34** | Both endpoints are certain; the *link* is not |
| `f06` | 0.74 | — | — | No candidate part at all |

`f02` tests a quieter failure: two confident part detections and no damage. A
model that pads the report by describing the undamaged bumper and hood has
invented findings.

## 4. How Prompt V1 was tested

Outputs were checked mechanically, not by reading them. The checker recomputes
each detection's expected classification from the fixture JSON — independently of
the report — and then verifies the report text agrees.

| Group | Checks |
|---|---|
| Classification | Every detection at or above `T_DAMAGE_REPORT` appears in Findings; every one below appears in the appendix and **only** there |
| Hedging | Detections in the hedge band carry a lexical hedge; those above it do not |
| Localisation | Recomputes LOCATED / AMBIGUOUS / UNLOCATED per Step 4 and confirms the report matches, including that an unlocated finding never names its candidate part |
| Ambiguity | Both candidates present, neither ranked |
| Part naming | A part class may appear only if some finding qualifies to name it |
| Prohibited vocabulary | 39 banned terms across severity, repair, cost, causation, timing, certainty and substituted labels |
| Numerics | No raw confidence value printed |
| Structure | Absence disclaimer present when empty; unusable image never conflated with a clean result; closing notice present |
| Duplication | No detection reported more than once |

The banned-term scan covers Findings and the appendix only. The mandated closing
notice legitimately contains "repair requirements or cost".

### Result

**All 9 LLM-generated outputs pass all checks.** No constraint violation was
observed in any output.

### Negative control

A passing checker is worthless if it cannot fail. `f07`'s output was temporarily
replaced with a deliberately non-compliant report — inventing a "hairline
crack", substituting "windscreen" for `front_glass`, adding severity, a repair
recommendation, a cost, a causal claim and a certainty word, and promoting the
suppressed dent into Findings. The checker reported **15 violations**, including
the three structural ones (`glass_shatter` finding missing, suppressed dent
leaked into Findings, appendix absent). The compliant output was then restored
and re-verified.

## 5. Observations for V2 (TASK-26)

1. **Grammar artefact.** `f07` produced "*A* shattered glass was detected on the
   front glass." The readable-rendering rule maps `glass_shatter` to "shattered
   glass" but does not say how to article it, and the model applied the "A
   {damage}…" sentence pattern mechanically. Cosmetic, but it is the kind of
   wording a reviewer notices. V1 is left as tested; V2 should give a rendering
   that reads naturally in sentence position.
2. **The unlocated phrasing collapses three distinct reasons.** `f04` (uncertain
   part), `f06` (no candidate) and `f08` (uncertain link) all produced "The
   affected part could not be determined." The model also chose that generic
   wording for `f08` over the prompt's more specific "…could not be determined
   with confidence", showing the two are interchangeable in practice.
   Distinguishing the reasons would be more informative to a reviewer, but risks
   leaking confidence internals into prose. A V2 decision, not a V1 defect.
3. **Suppressed detections carry no location.** Per TASK-24 §10 the appendix is
   class-only. In `f03` the reviewer is told a scratch was seen but not where,
   though the fixture has a confident back bumper and a 0.71 association.
   Deliberate; worth confirming it is what reviewers want.
4. **The hedge band is wide.** With the test values, a 0.31 and a 0.59 detection
   are phrased identically. A third band may be warranted once real values exist.
5. **Adversarial input is untested.** TASK-24 §6 forbids acting on instruction
   text planted inside a JSON string field. V1 states the rule; no fixture probes
   it. **Primary hardening target for V2.**
6. **Variance is unmeasured.** One sample per fixture (§2). V2 testing should
   resample to distinguish a robust prompt from a lucky run.
